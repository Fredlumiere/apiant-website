Проблема обеспечения прозрачности работы центрального оперативного центра

Сеть оздоровительных центров Mindbody, работающая по франшизе, управляет 23 филиалами под руководством централизованной операционной команды. Централизованная операционная система включает в себя CRM-систему (HubSpot), платформу для электронной почты (Klaviyo), инструмент бизнес-аналитики (Looker) и инструмент поддержки клиентов (Zendesk). Всем четырем системам необходимо иметь актуальную информацию о членстве и метаданных о местоположении во всех 23 филиалах.

Сегодня операционная группа еженедельно экспортирует CSV-файлы с каждого сайта Mindbody, объединяет их в скрипте и повторно импортирует в каждый последующий инструмент. К моменту поступления данные устаревают на неделю. Маркетинговые кампании запускаются для бывших пользователей. Заявки в службу поддержки перенаправляются не по тому адресу.

Проблема застоя существует и в плане пользовательского опыта. Пользователь, обращающийся в службу поддержки по поводу проблем с оплатой в офисе № 14, попадает на оператора, который работает с данными недельной давности. Оператор не знает текущего статуса пользователя, его местоположения или условий договора. Разговор длится вдвое дольше, и пользователь заканчивает его еще более расстроенным, чем начал. Умножьте это на сотни еженедельных обращений в службу поддержки, и показатель NPS франшизы снизится.

Какие местоположения и членства запускают отправку сообщений?

Универсальные интеграции работают для каждого отдельного объекта. Франшизе, насчитывающей 23 объекта, необходим единый поток данных в режиме реального времени для всех объектов, с прикрепленными метаданными о местоположении, чтобы последующие инструменты могли правильно фильтровать, направлять и сегментировать трафик.

Самостоятельно созданные скрипты могут генерировать фид, но требуют постоянного обслуживания: каждое изменение API Mindbody, каждый новый сайт, каждое изменение схемы нижестоящего потока — это ошибка. Большинство франшиз в итоге запускают скрипт еженедельно, потому что никто не доверяет ему настолько, чтобы запускать его чаще.

Разрастание интеграций на каждом сайте — это операционный долг, который незаметно накапливается. Каждый сайт со своей собственной интеграцией со своим собственным маркетинговым инструментом, своим собственным инструментом поддержки, своим собственным инструментом бизнес-аналитики представляет собой отдельную точку отказа и отдельную нагрузку по обслуживанию. Франшиза из 23 сайтов, использующая интеграции на каждом сайте, использует 23 отдельных стека интеграций. Когда что-то ломается, никто не знает, где, и никто не может это исправить, не углубившись в конфигурацию, специфичную для каждого сайта.

Подход APIANT

Функция поддержки нескольких локаций AppConnect управляет всеми 23 площадками в рамках одной подписки. Управление локациями обеспечивает обновление метаданных о местоположении в режиме реального времени (новые площадки, переименованные площадки, деактивированные площадки) для центрального операционного стека. Управление членством обеспечивает изменение статуса членства в режиме реального времени (активно, приостановлено, отменено, истекло) с указанием местоположения.

Zapier обрабатывает ленту новостей и перенаправляет обновления в HubSpot, Klaviyo, Looker (через BigQuery) и Zendesk. Команда эксплуатации получает единое представление о ситуации в режиме реального времени по всей франшизе. Кампании нацелены на текущих пользователей. Заявки в службу поддержки автоматически перенаправляются на нужный сайт.

Модель единой подписки AppConnect сводит на нет разрастание сети. Одна подписка обрабатывает все 23 сайта. Один набор веб-хуков доставляет все события. Одна конфигурация сопоставления обрабатывает всю нисходящую маршрутизацию. Когда франшиза добавляет сайт № 24, команда эксплуатации добавляет его в AppConnect, и данные начинают автоматически передаваться во все нисходящие инструменты. Никаких новых учетных записей Zapier, никакой настройки для каждого сайта, никакой репликации всей системы.

Версионирование схемы имеет большое значение в таком масштабе. По мере развития инструментов (HubSpot добавляет новое поле, Klaviyo реструктурирует списки, Zendesk меняет схему обработки заявок), интеграционный слой синхронизирует изменения один раз и распространяет их на все 23 сайта. Команда эксплуатации поддерживает одну каноническую схему, а не 23 разрозненные копии.

Разработка рабочего процесса «Главное представление операций»

  1. Активируйте коннекторы AppConnect для управления местоположением и управления членством. Поддержка нескольких местоположений позволяет обрабатывать все 23 площадки в рамках одной подписки.
  2. В Zapier можно создавать Zap-пакеты, которые распространяют обновления местоположения и членства в HubSpot, Klaviyo, Looker (с помощью шага записи BigQuery) и Zendesk.
  3. Для каждого инструмента, используемого в дальнейшем, настройте поле атрибуции местоположения, чтобы сегменты, кампании и правила маршрутизации могли корректно фильтровать данные.
  4. Заполните пробелы один раз: экспортируйте текущее местоположение и состояние членства и импортируйте их во все последующие инструменты для установления базового уровня.

  5. Начинайте работу в режиме реального времени. Еженедельный ритуал CSV-сбора данных командой эксплуатации завершен.

  6. Установите правила именования для всех инструментов. Сайт, названный «Downtown Wellness Center» в Mindbody, «DWC» в HubSpot и «Downtown» в Zendesk, — это настоящий кошмар для службы поддержки. В AppConnect функция определения местоположения автоматически передает каноническое название; команда эксплуатации обеспечивает согласованность на уровне интеграции.

  7. Тщательно спланируйте засыпку. Для обеспечения корректной работы системы автоматического заполнения баз данных на 23 площадках в HubSpot, Klaviyo, Looker и Zendesk необходимо соблюдать установленные ограничения скорости для каждого инструмента. AppConnect регулирует скорость первоначального заполнения и запускает процесс в режиме реального времени с момента переключения.

Репрезентативная операционная эффективность в 5 бассейнах

Гипотетический пример: сеть оздоровительных центров с 23 филиалами и примерно 16 000 активных абонементов. После синхронизации данных о местоположении и членстве в режиме реального времени через AppConnect, время, затрачиваемое командой на еженедельный процесс экспорта-слияния-импорта, сокращается с примерно 12 часов в неделю до нуля. Количество рассылок по электронной почте бывшим участникам (срабатывающих по ошибке из-за устаревших данных) снижается до нуля. Количество неправильно перенаправляемых заявок в службу поддержки снижается примерно с 8 процентов до менее 1 процента.

Стратегическая ясность повышается на уровне руководства. Генеральный директор франшизы видит единое представление о росте числа членов по всем 23 точкам в режиме реального времени. Сравнение показателей на уровне отдельных точек становится сопоставимым. Решения о том, в какие точки инвестировать, какие объединить и где открыть следующую, принимаются на основе актуальных, достоверных и сопоставимых данных. Интеграция становится стратегическим активом, а не просто тактической автоматизацией.

Нестандартные ситуации, о которых стоит знать

Приобретение и продажа активов — это операционная реальность для растущих франшиз. AppConnect обрабатывает новый объект, добавляя его в подписку; поток данных начинается немедленно. Проданный объект можно приостановить, что остановит поток данных без потери исторических записей.

Изменения уровня членства (переход с базового на премиум, понижение уровня) распространяются как обновления, а не как новые подписки. Инструменты, работающие с предыдущими уровнями, видят изменение уровня и соответствующим образом обновляют сегментацию. Маркетинговые кампании, нацеленные на старый уровень, прекращают работу с данным участником; запускаются кампании для нового уровня.

Перенос пользователей между филиалами (когда пользователь переезжает из одного города в другой и меняет свой основной филиал) происходит с сохранением той же учетной записи. AppConnect сохраняет историю пользователя, одновременно обновляя его местоположение, поэтому показатели LTV и вовлеченности не сбрасываются при переносе. Пользователи чувствуют, что их знают во всей сети, а не анонимно на каждом новом филиале.

Выводы для строителей

  • Для франчайзинговых сетей с несколькими филиалами необходимы данные в режиме реального времени, а не еженедельные. Цена устаревших данных видна в каждом инструменте, используемом в дальнейшем.
  • Одна подписка, все сайты, единый канал. Разрастание интеграции на каждом сайте — это операционный долг.
  • Определение местоположения на уровне интеграции является основой для каждой последующей сегментации, кампании и правила маршрутизации.
