フランチャイズの主導権争い

複数の店舗を展開するブティックジムブランドでは、ほぼ必ず同じような社内抗争が起こります。見込み客が企業のウェブサイトのフォームに記入します。クリックしたのは企業のマーケティング部門です。見込み客はフランチャイズAの近くに住んでいて、フランチャイズBの近くで働いています。最初の1ヶ月で両方のジムを訪れます。見込み客の所有権は誰にあるのか？コミッションは誰にあるのか？見込み客を呼び込んだ広告費は誰が支払うのか？

仮説：Tradewind Athletic Network（例示）は、12店舗を展開し、7,200人の会員を抱えるフランチャイズブランドです。各フランチャイズ加盟店は独自のHighLevelサブアカウントを運用し、本社はブランド全体のマーケティングを管理しています。統合に明確なルーティングルールが組み込まれていないため、複数の店舗にまたがる会員同士のやり取りは、Slack上での議論の火種となりかねません。

既製ツールがフランチャイズ規模で失敗する理由

複数拠点のHighLevelとMindbodyを同時に使用すると、サブアカウントの問題とサイトIDの問題が発生します。ほとんどの汎用ツールは、どちらか一方しか処理できません。

  • 彼らは郵便番号に基づいてルートを選定する（ただし、郵便番号は市の境界で途切れ、会員が実際に利用するジムは考慮されない）。
  • それらのデータは、単一の「中央」HighLevelアカウント（フランチャイズ加盟店はアクセスできない）にルーティングされる。
  • これらは複数のHighLevelサブアカウントにルーティングされますが、重複排除機能がないため、同じメンバーが2つのサブアカウントに連絡先を作成することになります。

カスタム構築は有効ですが、新しいフランチャイズがオープンしたり、サブアカウントが再構成されたり、会員が別のジムに移籍したりするたびに、継続的なメンテナンスが必要になります。統合こそが境界線となるべきであり、企業のオペレーションマネージャーが手作業で管理するスプレッドシートであってはなりません。

APIANTアプローチ

CRMConnect Mindbody to HighLevel の内容 マルチロケーション・サポート まさにこのケースのために設計された、一流の機能です。APIアプリのページには、「単一のHighLevelアカウントと同期された複数のMindbodyサイトを効率的に管理します。フランチャイズや複数拠点を持つビジネスに最適で、リードをそれぞれのMindbody拠点に自動的にルーティングします。」と記載されています。複数のサブアカウントを持つフランチャイズネットワークの場合、同じルーティングロジックがサブアカウントごとに適用されます。

フランチャイズモデルを支える特徴：

  • マルチロケーション・サポート サイトとサブアカウントのマッピングのため。
  • 双方向クライアント同期 つまり、企業が獲得した見込み客情報は、適切なフランチャイズのMindbodyサイトに誘導されるということだ。
  • スマートな重複プロフィール処理 つまり、複数拠点のメンバーは連絡先が1つであり、2つではないということです。
  • 140以上のカスタムコンタクトフィールド つまり、自宅所在地、第二の所在地、および最終訪問場所はすべて、クエリ可能な属性として存在します。

CRMConnectにおける複数拠点ルーティングの仕組み

設定は簡単です。

  1. 各MindbodyサイトはCRMConnectに安定した状態で登録されています site_id.
  2. HighLevelの各サブアカウントは安定した subaccount_id.
  3. サイトとサブアカウントのマッピングが定義されています。 site_id -> subaccount_id.
  4. 新規リード（集中型キャプチャフォームから）のルーティングルール：
  5. リードフォームにロケーションタグが含まれている場合は、マッピングされたサブアカウントにルーティングし、マッピングされたMindbodyサイトにプッシュします。
  6. タグがない場合は、トリアージのために「中央」の保留サブアカウントにルーティングします。
  7. 既存メンバーのルーティングルール：
  8. 会員 mindbody_home_location このフィールドは、プライマリサブアカウントを定義します。
  9. 異なる拠点への訪問は、同じ連絡先のホームサブアカウント内のイベントとして記録されます。

スマートな重複防止ロジックにより、最もよくある失敗、つまり同じメールアドレスで同じ週にサイトAとサイトBの両方に登録してしまう事態を防ぎます。CRMConnectは一致する登録を検出し、単一の連絡先に統合し、プロファイルに両方の場所をタグ付けします。

重複なくサイトをサブアカウントにマッピングする

Routing configuration:
site-01 (Downtown) -> subaccount-tradewind-downtown
site-02 (Pearl)    -> subaccount-tradewind-pearl
site-03 (Eastside) -> subaccount-tradewind-eastside
...
site-12 (Airport)  -> subaccount-tradewind-airport

HighLevel contact custom fields:
- mindbody_home_location_id          primary site, drives sub-account ownership
- mindbody_home_location_name
- mindbody_visited_sites_30d         list of site_ids
- mindbody_last_visit_site_id        most recent visit location
- mindbody_lead_source_site_id       set at lead capture, never overwritten

の home_location_id リード所有権フィールドです。リードが有料会員になった時点で設定され、文書化されたプロセス（会員が都市を移動、メインのジムが変更）を通じて再割り当てできます。 visited_sites_30d このフィールドは、所有権を変更することなく、複数の拠点間の活動を捉えます。

アカウントなしでのクロスサイトメンバーアクティビティ Crossfire

本社運営チームは、すべてのサブアカウントを網羅した明確なビューを得られます。各フランチャイズ加盟店は、自身の連絡先のみを確認できます。拠点間の活動は、適切な場所に記録されます。

  • 会員のホームサブアカウント：完全な履歴、主要連絡先記録。
  • 訪問した（自宅以外の）サイトのレポート：連絡先レコードとしてではなく、「ゲスト訪問」セグメントに表示されます。

サイトBのフランチャイズ加盟店は、サイトAの会員が頻繁にジムを訪れていることに気づき、本社運営プロセスを通じて会員の移転を申請できます。システムは移転をサポートしますが、どちらのフランチャイズ加盟店も直接連絡先を取得することはできません。このルールは統合レイヤーで適用されます。

結果として、Slackでの議論は発生しません。所有権は一元化されます。複数拠点間で発生した収益は、リードを獲得した拠点ではなく、利用状況に基づいて収益を上げた拠点に帰属します。

7,200人規模における代表的な運用能力

あくまでも参考例であり、実際の顧客像ではありません。

  • HighLevelサブアカウント全体における重複連絡先数（四半期ごと）：定期的なクリーンアップ作業から、四半期あたり約5～15件の統合へと減少しました。
  • フランチャイズ関連の紛争解決に費やす企業運営の週あたりの時間：約6～10時間（回収済み）。
  • 中央集約型のリードの場合、リードから初回訪問までの時間が1～2日短縮されます。これは、手動での引き継ぎではなく、受付時にルーティングが行われるためです。
  • メンバーの移籍リクエストは、（場当たり的な対応ではなく）すべて一つのプロセス内で処理されます。これは、統合によって単一のホームロケーションが強制されるためです。

この動きは主に政治的なものだ。統合によって所有権ルールを交渉ではなく制度化することで、議論は終結する。

ビルダーテイクアウト

  • サイトとサブアカウントのマッピングを統合に組み込んでください。スプレッドシートでのルーティングは、3つ以上のフランチャイズには対応していません。
  • 使用 home_location_id 単一所有権の分野として扱われます。複数拠点間の訪問は活動であり、所有権の主張ではありません。
  • 統合機能によって重複排除が強制されます。境界でのスマートなマッチングにより、四半期ごとのクリーンアップ作業を削減できます。
