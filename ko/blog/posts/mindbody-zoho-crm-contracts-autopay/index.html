월말 계약 보고서가 쓸모없는 이유

계약 기반 멤버십은 자동 결제가 실패하기 전까지는 예측 가능한 수익원입니다. 하지만 결제 실패 시점은 매우 짧습니다. 결제가 실패한 시점부터 24시간에서 72시간 이내에 회원은 다른 스튜디오를 알아볼 가능성이 높습니다. 대부분의 스튜디오는 매달 1일에 계약 현황 보고서를 발행하는데, 이는 3일에 발생한 결제 실패가 27일 동안 기록되지 않는다는 것을 의미합니다. 보고서가 발행될 즈음에는 회원이 이미 다른 스튜디오를 찾고 있을 가능성이 큽니다.

가상 사례: 미러 레이크 필라테스(예시)는 단일 지점을 운영하는 스튜디오로, 360명의 계약 고객을 보유하고 있습니다. 영업팀은 Zoho CRM을 사용하여 모든 업무를 처리하지만, 계약 세부 정보는 Mindbody PDF 파일에 저장됩니다. 월말 정산에 반나절이 소요됩니다. 자동 결제 실패는 28일째에 발견되지만, 약 30% 정도만 복구되고 나머지는 이탈합니다.

시중에서 판매되는 도구가 여기서 실패하는 이유

Mindbody 계약은 여러 상태 변화를 가진 중첩 객체입니다. 대부분의 일반적인 연결 도구는 계약 생성 시에만 계약을 가져오고 업데이트는 하지 않습니다. 자동 결제 상태, 재시도 횟수, 예약된 변경 사항, 취소 타임스탬프는 모두 하위 객체에 저장되어 있으며, 이를 새로 고치려면 특정 API 호출이 필요합니다.

진정한 해결책은 다음과 같아야 합니다:

  • 계약을 살아있는 상태를 가진 별도의 객체로 취급하십시오.
  • 자동 결제 상태 변경 사항을 거의 실시간으로 이벤트로 푸시합니다.
  • 안전장치로서 "현재 상태"를 매일 재계산합니다.

맞춤형 구축은 이러한 방식을 사용하지만, 360개 계약에 걸쳐 일일 정산을 처리하는 데 필요한 요금 제한은 두 달 만에 문제가 발생하는 종류의 문제입니다.

APIANT 접근법

CRMConnect Mindbody와 Zoho CRM에는 전용 기능이 포함되어 있습니다. MB 계약 사용자 정의 객체와 함께 MB 멤버십API 앱 페이지에서 발췌: "고객 계약 세부 정보와 자동 결제 상태를 Zoho CRM에 지속적으로 동기화합니다."

이를 뒷받침하는 특징은 다음과 같습니다.

  • 멤버십 및 계약 동기화 MB Contracts를 전용 사용자 정의 개체로 사용합니다.
  • 실시간 데이터 동기화 따라서 자동 결제 상태 변경 사항은 몇 초 내에 Zoho CRM에 반영됩니다.
  • 종합 구매 및 결제 이를 통해 기본 결제 이벤트도 조회할 수 있습니다.
  • 사용자 지정 개체 매핑 따라서 계약서는 업무 흐름 및 보고서에서 가장 중요한 기록물입니다.

통합 데이터 처리 엔진은 중첩된 계약 페이로드를 처리하고 각 하위 상태를 Zoho 객체 스키마에 깔끔하게 매핑합니다.

MB Contracts가 Zoho CRM에 제공하는 정보는 무엇인가요?

MB Contracts 사용자 정의 개체에는 실제 워크플로에 필요한 모든 필드가 포함되어 있습니다.

Zoho CRM custom object: MB Contracts
- contract_id
- contact_id (links to Zoho CRM contact)
- contract_name                e.g. "12-Month Unlimited Reformer"
- start_date / end_date
- status                       active|pending_cancel|expired|terminated
- autopay_status               current|retrying|failed|suspended
- autopay_method               card|ach
- autopay_next_charge_date
- autopay_next_charge_amount
- autopay_last_attempt_at
- autopay_last_attempt_result  success|declined|insufficient_funds|...
- autopay_retry_count
- monthly_amount
- balance_remaining

그만큼 autopay_status 해당 필드는 모든 중요한 사항의 트리거입니다. 상태가 변경됩니다. failed or retrying워크플로가 실행되고 복구가 시작됩니다.

결제 실패 복구 워크플로 설계

Zoho CRM의 MB 계약 객체에 대한 워크플로:

  1. 방아쇠: autopay_status 변화 current to failed or retrying.
  2. 같은 시간: 고객에게 "안녕하세요, 저희 시스템에서 결제가 완료되지 않은 것으로 확인되었습니다. 빠른 업데이트는 여기에서 확인하세요: [업데이트 카드 링크]. 도움이 필요하시면 'HELP'라고 답장해 주세요."라는 내용의 SMS를 자동 전송합니다.
  3. +4시간: 결제 상태가 여전히 실패로 표시되고 고객이 카드 정보를 업데이트하지 않은 경우, 전체 상황 정보(마지막 성공 결제, 재시도 횟수, 금액)를 포함하여 멤버십 전문가에게 우선순위가 높은 작업을 생성하십시오.
  4. +24시간: 스튜디오 소유주가 보낸 자동 이메일: "잠깐 전화드릴까요?"
  5. +48시간: 담당자에게 연락해야 하는 일정이 생성되었으며, 당일 통화 예정입니다.
  6. 복구 분기: 언제 autopay_status 다시 뒤집힙니다 current남은 작업을 중단하고 확인 SMS를 보냅니다.
  7. 에스컬레이션 분기: 5일 이상 해결되지 않으면 리드 상태가 "위험 회원"으로 변경되고 대면 유지 상담 일정이 잡힙니다.

당일 SMS 알림 서비스는 대부분의 거래량을 복구합니다. 카드 사용 실패는 대개 카드 만료 또는 잔액 부족으로 인해 발생하며, 회원은 이러한 사실을 알지 못하는 경우가 많습니다. 몇 주가 아닌 몇 시간 내에 실패를 파악하는 것이 복구율을 높이는 가장 중요한 요소입니다.

갱신 날짜를 파이프라인 예측으로 활용

그만큼 end_date MB Contracts 객체의 필드를 통해 영업팀은 갱신 수익을 몇 주 전에 예측할 수 있습니다.

  • 90일 선행 파이프라인: 합계 monthly_amount 계약의 경우 end_date 향후 90일 동안의 갱신율은 과거 갱신율을 기준으로 가중치를 부여합니다.
  • 갱신 문의 대기열: 계약 대상 end_date - now() <= 45 days 그리고 status = active고객 생애 가치(CLTV) 순으로 정렬되었습니다.
  • 자동 갱신과 수동 갱신 분할: 기본 멤버십의 갱신 플래그를 기준으로 필터링하고 수동 갱신 측에 필요한 인력을 계획합니다.

예측은 데이터가 실시간으로 업데이트될 때만 유용합니다. 월말 보고서는 입력 데이터가 오래되었기 때문에 예측치가 5~15% 정도 틀리는 경우가 많습니다.

Sample forecast query (Zoho CRM Reports):
  Select contact_id, monthly_amount, end_date
  From MB_Contracts
  Where end_date Between today() And today() + 90 days
    And status = 'active'
  Order By client_ltv DESC

360명의 고객을 대상으로 한 대표 회복률

이 이미지는 예시용 합성 이미지이며 실제 고객의 모습이 아닙니다.

  • 자동 결제 실패 복구율 기준치(월말 기준): 약 25~35%.
  • 당일 SMS 발송 및 24시간 이내 소유자 이메일 발송을 통한 회수율 향상: 60~75% 범위로 상승.
  • 조기 오류 감지를 통해 분기별로 절감되는 수익: 평균 계약 규모에 따라 계약 기반에서 상당한 비중을 차지합니다.
  • 소유주가 계약 조정에 매달 투입하는 시간은 약 4시간에서 1시간 미만으로 줄어들었으며, 남은 시간은 실제로 위험에 처한 구성원들을 지원하는 데 사용됩니다.

이 메커니즘은 빠른 감지와 구성원이 실제로 응답할 수 있는 일련의 과정을 제공합니다. 통합 기능은 감지를 제공하고, 해당 과정은 업데이트를 요청하는 데 있어 정직해야 합니다.

건설업체 테이크아웃

  • 계약과 멤버십을 별도의 사용자 정의 객체로 취급하세요. 고객은 멤버십 하나와 계약 세 개를 가질 수 있습니다(또는 그 반대). 개념별로 레코드를 하나씩만 보유하면 쿼리가 간결해집니다.
  • 결제 실패 복구 기능을 구축하세요. autopay_status 예정된 보고서가 아닌 변경 이벤트입니다. 지연 시간이 핵심입니다.
  • 사용 end_date 갱신 파이프라인 예측치로 활용하세요. 이는 스튜디오가 보유한 가장 신뢰할 수 있는 미래 수익 수치입니다.
