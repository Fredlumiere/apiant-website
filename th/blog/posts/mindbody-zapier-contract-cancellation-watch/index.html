#ฟิตเนสและสุขภาพ#จิตใจและร่างกาย#แซเปียร์#AppConnect#การซิงค์แบบสองทิศทาง

เหตุใดขั้นตอนการยกเลิกจึงมักล่าช้าเสมอ

เครือข่ายฟิตเนสขนาดเล็กแห่งหนึ่งขายสัญญาสมาชิกรายปี การยกเลิกเป็นสิ่งที่หลีกเลี่ยงไม่ได้แต่ก็มีค่าใช้จ่ายสูง เมื่อสมาชิกยกเลิก เครือฟิตเนสต้องการให้เกิดสามสิ่งพร้อมกัน: ส่งอีเมลเพื่อรักษาฐานลูกค้าภายในหนึ่งชั่วโมง อัปเดตข้อมูลสมาชิกใน HubSpot ด้วยเหตุผล "ขาดการติดต่อ" และหัวหน้าฝ่ายดูแลลูกค้าได้รับการแจ้งเตือนทาง Slack ให้โทรหาลูกค้าโดยตรงหากมูลค่าตลอดอายุการใช้งานของลูกค้า (LTV) สูงพอ

ปัจจุบันนี้ ไม่มีอะไรเกิดขึ้นโดยอัตโนมัติแบบนี้แล้ว การยกเลิกสมาชิกจะปรากฏในรายงานของ Mindbody ในเช้าวันถัดไป การพยายามรักษาสมาชิกไว้จะเกิดขึ้นหลังจากนั้นหลายวัน หรืออาจจะไม่เกิดขึ้นเลยด้วยซ้ำ และถึงตอนนั้น สมาชิกก็อาจจะไปใช้บริการฟิตเนสแห่งใหม่ที่อยู่ใกล้ๆ กันแล้ว

นอกจากนี้ยังมีปัญหาเรื่องวัฒนธรรมองค์กรด้วย เมื่อการยกเลิกปรากฏเฉพาะในรายงานรายเดือน ทีมดูแลลูกค้าจึงไม่มีจังหวะในการตอบสนอง การพูดคุยเรื่องการรักษาฐานลูกค้าจึงกลายเป็นการประชุมทบทวนรายไตรมาสที่ทุกคนเห็นพ้องต้องกันว่าการรักษาฐานลูกค้าเป็นสิ่งสำคัญ แต่แล้วก็ไม่มีใครลงมือทำอะไร เพราะงานดูซับซ้อนเกินไป เหตุการณ์การยกเลิกแบบเรียลไทม์จะสร้างจังหวะการแก้ไขปัญหาประจำวันที่ส่งผลให้ตัวชี้วัดดีขึ้นจริง ๆ

สิ่งที่ Client Contract Trigger ส่งไปยัง Zapier

API การจัดการสัญญาของ Mindbody นั้นซับซ้อน ตัวเชื่อมต่อ Zapier ดั้งเดิมไม่แสดงการยกเลิกสัญญาของลูกค้าเป็นตัวกระตุ้นแบบเรียลไทม์ การตรวจสอบด้วยตนเองสามารถตรวจจับได้ แต่จะทำให้เกิดความล่าช้าและปัญหาเรื่องโควต้า

เว็บฮุคบริดจ์ทั่วไปส่งข้อมูลที่มีขนาดเล็กมาก จากนั้น Zap ต้องเรียกใช้ API เพิ่มเติมเพื่อเพิ่มข้อมูลให้ครบถ้วน เช่น มูลค่าตลอดชีพของสมาชิก มูลค่าสัญญา และตำแหน่งที่ตั้ง การเรียกใช้ API เพิ่มเติมแต่ละครั้งหมายถึงขั้นตอนการตรวจสอบสิทธิ์เพิ่มเติม ข้อจำกัดด้านอัตราการใช้งาน และโหมดความล้มเหลวเพิ่มเติม

เหตุผลในการยกเลิกมักไม่มีโครงสร้างที่ชัดเจนในระบบส่วนใหญ่ ช่องข้อความอิสระที่ระบุว่า ‘ทำไมคุณถึงยกเลิก’ นั้นยากต่อการดำเนินการ รหัสเหตุผลที่กำหนดโครงสร้างไว้ (เช่น ราคา การย้ายที่อยู่ ตารางเวลา ความไม่พอใจ ปัญหาสุขภาพ อื่นๆ) ช่วยให้สามารถวิเคราะห์ในระดับกลุ่มได้ เช่น เหตุผลใดที่เติบโตเร็วที่สุด แคมเปญใดที่รักษากลุ่มใดได้ดีที่สุด และโอกาสในการรักษาลูกค้าไว้ได้จริงอยู่ที่ใด เว็บฮุคทั่วไปไม่ได้บังคับใช้โครงสร้างนี้

แนวทาง APIANT

ตัวเชื่อมต่อการจัดการสัญญาของลูกค้าของ AppConnect จะส่งคำขอเว็บฮุคแบบเรียลไทม์เมื่อมีการสร้าง อัปเดต หรือยกเลิกสัญญา โดยข้อมูลที่ส่งไปจะได้รับการปรับปรุงให้สมบูรณ์ยิ่งขึ้น ได้แก่ รหัสสมาชิก ชื่อ ประเภทสัญญา มูลค่ารายเดือน มูลค่าสัญญารวม วันที่เริ่มต้น เหตุผลในการยกเลิก สถานที่ และมูลค่าตลอดอายุการใช้งานของลูกค้า (LTV) ปัจจุบัน

Zap จะประมวลผลข้อมูลที่ได้ปรับปรุงแล้วและส่งต่อไปยังการดำเนินการถัดไป ได้แก่ การส่งอีเมลผ่าน Klaviyo พร้อมข้อเสนอการรักษาลูกค้า การอัปเดตสถานะดีลใน HubSpot การแจ้งเตือนผ่าน Slack ไปยังหัวหน้าฝ่ายความสำเร็จของลูกค้าพร้อมชื่อสมาชิก มูลค่าตลอดอายุการใช้งานของลูกค้า (LTV) และลิงก์ ‘โทรเลย’ การกระตุ้นเพียงครั้งเดียว ส่งผลให้เกิดการดำเนินการถัดไปที่มีคุณภาพสูงมากมาย โดยทั้งหมดเกิดขึ้นภายในไม่กี่นาทีหลังจากการยกเลิก

ข้อมูลที่ AppConnect รวบรวมไว้ประกอบด้วยรหัสเหตุผลการยกเลิกและข้อความแสดงความคิดเห็นแบบอิสระ ระบบอัตโนมัติในขั้นตอนถัดไปสามารถแยกย่อยตามรหัสนี้ได้ เช่น การยกเลิกเนื่องจากราคาจะได้รับข้อเสนอส่วนลด การยกเลิกเนื่องจากตารางเวลาจะได้รับแคมเปญเกี่ยวกับความยืดหยุ่นของเวลาเรียน การยกเลิกเนื่องจากการย้ายที่อยู่จะได้รับการแนะนำไปยังสตูดิโอพันธมิตรในสถานที่ใหม่ (และหลีกเลี่ยงการเสียเวลาไปกับการยกเลิกที่ไม่สามารถกู้คืนได้)

ระบบการกำหนดเส้นทางการติดต่อแบบมีเงื่อนไขของ Slack ขยายไปถึงการพยายามรักษาลูกค้าที่มีมูลค่าตลอดอายุการใช้งานสูง (LTV) หัวหน้าทีมดูแลลูกค้าไม่ได้โทรหาลูกค้าที่ยกเลิกทุกราย แต่จะโทรหาเฉพาะลูกค้าที่มูลค่าตลอดอายุการใช้งาน (LTV) สูงพอที่จะคุ้มค่ากับเวลาที่เสียไป ฟิลด์ LTV ที่ครบถ้วนของ AppConnect ทำให้การกำหนดเส้นทางการติดต่อเป็นเรื่องง่าย ลูกค้าที่ยกเลิกด้วย LTV สูงจะได้รับการโทรติดต่อในวันเดียวกัน ลูกค้าที่ยกเลิกด้วย LTV ปานกลางจะได้รับการส่งอีเมลอัตโนมัติ และลูกค้าที่ยกเลิกด้วย LTV ต่ำจะได้รับการส่งอีเมลบอกลาและแจ้งเตือนให้กลับมาใช้บริการอีกครั้งในอีกหกเดือนต่อมา

การออกแบบขั้นตอนการทำงานเพื่อช่วยเหลือสมาชิกในวันเดียวกัน

  1. เปิดใช้งานตัวเชื่อมต่อการจัดการสัญญาของลูกค้าของ AppConnect สำหรับบัญชี Mindbody ของยิม
  2. ใน Zapier ให้สร้าง Zap ที่ทำงานโดยอัตโนมัติเมื่อได้รับข้อความว่า ‘สัญญาถูกยกเลิก’ ข้อความดังกล่าวจะมาพร้อมกับข้อมูลเพิ่มเติม
  3. เพิ่มขั้นตอน Klaviyo เพื่อส่งอีเมลรักษาฐานลูกค้าพร้อมข้อเสนอพิเศษที่เขียนโค้ดเอง
  4. เพิ่มขั้นตอนใน HubSpot เพื่ออัปเดตสถานะของดีลเป็น 'ปิดดีลไม่สำเร็จ' พร้อมระบุเหตุผลการยกเลิก
  5. เพิ่มขั้นตอนแบบมีเงื่อนไขใน Slack: หากมูลค่าตลอดอายุการใช้งานของลูกค้า (LTV) เกิน 2,000 ดอลลาร์ ให้แจ้งหัวหน้าทีมดูแลลูกค้าทันที

  6. ทดสอบโดยการยกเลิกสัญญาทดสอบ ตรวจสอบว่าการดำเนินการทั้งสี่อย่างในขั้นตอนถัดไปทำงานเสร็จภายในไม่กี่นาที

  7. สร้างการคำนวณ LTV ในขั้นตอนต้นทาง AppConnect สามารถคำนวณ LTV โดยอิงจากมูลค่าและระยะเวลาของสัญญา และ Zap จะนำค่าที่ได้ไปใช้โดยตรง หากเครือข่ายมีโมเดล LTV ที่ซับซ้อนกว่าในเครื่องมือ BI ของตน Zap สามารถเรียกใช้เครื่องมือ BI เพื่อขอค่าที่สมบูรณ์ยิ่งขึ้นและส่งต่อไปยังปลายทางนั้นได้

  8. ตั้งค่า SLA สำหรับการพยายามบันทึกข้อมูล หัวหน้าทีมดูแลความสำเร็จของลูกค้าจะพยายามแก้ไขปัญหาภายใน 4 ชั่วโมงทำการหลังจากลูกค้าแจ้งยกเลิกบัญชีที่มีมูลค่าตลอดอายุการใช้งานสูง (LTV) การแจ้งเตือนใน Slack จะมีเวลาตามข้อตกลงระดับบริการ (SLA) กำกับอยู่ด้วย ทำให้สามารถตรวจสอบความรับผิดชอบได้ในขั้นตอนการทำงาน

อัตราการออมโดยเฉลี่ยจากลูกค้า 310 ราย

สมมติฐาน: เครือข่ายฟิตเนสขนาดเล็ก 8 สาขา มีสมาชิกประมาณ 5,400 คน และมีการยกเลิกสัญญาประมาณ 60 รายต่อเดือน หลังจากเปิดใช้งานเวิร์กโฟลว์การยกเลิกสัญญาแบบเรียลไทม์ผ่าน AppConnect เวลาเฉลี่ยจากการยกเลิกจนถึงการพยายามรักษาลูกค้าไว้ลดลงจากประมาณ 36 ชั่วโมง เหลือต่ำกว่า 15 นาที อัตราการรักษาลูกค้า (เปอร์เซ็นต์ของสมาชิกที่ยกเลิกสัญญาแล้วกลับมาสมัครใหม่ภายใน 30 วัน) เพิ่มขึ้นจากประมาณ 7 เปอร์เซ็นต์ เป็นประมาณ 18 เปอร์เซ็นต์ รายได้ประจำปีโดยประมาณที่ได้รับคืนจากการรักษาลูกค้าไว้ได้อยู่ในช่วง 140,000 ถึง 190,000 ดอลลาร์ต่อปี

ผลกระทบแบบทบต้นต่อมูลค่าตลอดอายุการใช้งานของลูกค้า (LTV) นั้นมีความสำคัญอย่างยิ่ง กลุ่มลูกค้าที่คงอยู่ได้ถึง 30 เปอร์เซ็นต์ แทนที่จะเป็น 7 เปอร์เซ็นต์ จะทำให้ฐานสมาชิกเติบโตขึ้นเรื่อย ๆ ในระยะเวลาหลายปี เครือข่ายนี้ไม่ได้แค่ช่วยรักษาฐานสมาชิกแต่ละรายเท่านั้น แต่ยังช่วยปรับปรุงอัตราการเติบโตให้ดีขึ้นด้วย กระบวนการยกเลิกแบบเรียลไทม์เป็นหนึ่งในระบบที่มีผลตอบแทนจากการลงทุน (ROI) สูงที่สุดที่ธุรกิจที่มีรายได้ประจำสามารถนำไปใช้ได้

กรณีพิเศษที่ควรรู้

การหยุดชั่วคราวกับการยกเลิกนั้นแตกต่างกันอย่างมาก ลูกค้าที่หยุดการเป็นสมาชิกชั่วคราว (ซึ่งมักเกิดขึ้นเนื่องจากการเดินทางหรือการบาดเจ็บ) ไม่เหมือนกับการยกเลิก AppConnect จะส่งเหตุการณ์การหยุดชั่วคราวและการกลับมาใช้งานแยกต่างหากจากเหตุการณ์การยกเลิก ดังนั้นการติดต่อเพื่อรักษาฐานลูกค้าจึงไม่เกิดขึ้นเมื่อสมาชิกหยุดใช้งานชั่วคราวและสร้างความรำคาญใจให้สมาชิก

ความล้มเหลวในการต่ออายุอัตโนมัติ (บัตรเครดิตหมดอายุ หรือต้องอัปเดตบัตรใหม่) แตกต่างจากการยกเลิกโดยสมัครใจ และควรเรียกใช้เวิร์กโฟลว์ที่แตกต่างกัน: การแจ้งเตือนให้อัปเดตวิธีการชำระเงิน แทนที่จะเป็นการเสนอขอคงสถานะลูกค้า AppConnect แยกแยะเหตุผลการยกเลิกและแยกสาขา Zap อย่างเหมาะสม

เหตุการณ์การเปิดใช้งานใหม่ช่วยปิดวงจร สมาชิกที่เคยถูกยกเลิกแล้วกลับมาอีกครั้งจะทำให้เกิดเหตุการณ์การเปิดใช้งานใหม่ ระบบ Zap สามารถอัปเดต CRM เป็น ‘ได้สมาชิกกลับคืนมา’ และตัวชี้วัดอัตราการรักษาลูกค้าจะอัปเดตโดยอัตโนมัติ การรายงานการรักษาลูกค้าจะกลายเป็นแดชบอร์ดที่น่าเชื่อถือแบบเรียลไทม์ แทนที่จะเป็นการทบทวนรายไตรมาส

ผู้สร้างบ้าน

  • ระยะเวลาการเก็บรักษาข้อมูลหมดลงอย่างรวดเร็ว นาทีมีความสำคัญมากกว่าวัน
  • การเพิ่มข้อมูลสำคัญในขั้นตอนการเรียกใช้งานจะช่วยลดจำนวนการเรียกใช้ API ในขั้นตอนถัดไปและลดโอกาสเกิดข้อผิดพลาด
