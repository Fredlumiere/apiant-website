Code cannot be safely edited by a machine, inspected by a non-developer, or replayed with its state intact.

The AI builds your integration as a visual flow your team can open, read, and change. Not as code only its author understood.

And that holds at every layer: the flow, the connectors inside it, each API operation, every mapping, every setting. All of it is structured data. That one choice is why a machine can edit it safely, a person can always inspect it, and a saved run can be replayed with its state intact.

In September, the engineer who supervised that session has left, and Dana, the new integrations lead (sharp, technical, not a developer), needs to change how invoice line items map for a segment of customers. The question that decides Dana's week: what did the AI actually hand Meridian in March?

04 · A deterministic compiler that refuses structurally invalid work before it exists

The scenario

Halvorsen Mutual: 6,200 hail claims ride on a generated payments integration

Halvorsen Mutual writes crop insurance for 8,900 farms across Nebraska and Kansas. After a hail week in June, 6,200 claims queue up, average payout $18,400, and the integration that pushes approved amounts into the payments system was generated last month. It compiled cleanly and it deployed cleanly. Dee Ostergaard, the claims supervisor, is the person who learns whether it wrote the approved amount or the estimate into the payment field, and she learns it from farmers on the phone.

The AI's intent passes through a constrained schema; the compiler refuses invalid structures at the door. It then tests the build on a real saved claim and reads what reached the payment field. Dee can open that run too.

There is a real gate, so start with it. "The build command operates in 2 phases: 1. A TypeScript compilation runs to check types for all of your workflows and integration configurations", and their documented failure modes are dependency breakage of exactly the useful kind, including "Incorrect step output path referenced". Break a shared step and the project fails to build rather than shipping. What the gate checks is types, not intent. Nothing in it inspects whether the approved amount or the estimate reached the payment field: the Release checks Paragon publishes are configuration-level (missing OAuth app configuration, missing Environment Secret, changed App Event schema, changed scopes, removed integration, a new required User Setting, a default-enabled workflow, a changed trigger type), and the deployment's verdict arrives afterwards, in their words: "Error Messages appear after a Release has been deployed, if any unexpected failures occurred during the deployment." The type check is switchable by a documented flag, "you can attempt a build that suppresses these types of errors with the --skip-type-errors flag", and a workflow built in the dashboard never passes through the compilation at all. A person can catch a mapping error before production, and the row should say so plainly. Their build page documents a Test Step button per step, a Test Workflow button for the whole path, and the full-fidelity route: "To test the workflow without these limitations, use a live Connected User." What is sampled is the in-editor test, "Arrays are truncated to 20 items maximum / Paginated requests will only send 3 requests maximum." What their marketing promises is the automated version of that check, "Run tests. Easily run unit tests or end-to-end tests of entire workflows in-line", while the shipped CLI at 1.1.12 carries twelve commands and no test command. Dee's 6,200-claim queue is where a hand-run sampled check and a semantic error meet.

The scenario

Cardwell Staffing: 60 trusts, 60 drifting copies of one shift lookup

Cardwell Staffing places 2,300 agency nurses a week across 60 NHS trusts, each running its own rostering system. The logic that finds available shifts by ward was built once, then copied into all 60 integrations, and a timezone correction made in February reached 41 of the copies. Marcus asks the AI which integrations run the shift lookup; it names the referencing assemblies and the automations using them. Built once, fixed once: all 60 trusts inherit it. He can walk the list himself.

Concede the code half in the opening line, because it is genuine engineering. Paragraph reuse is ordinary module reuse with a documented convention: "You can export step definitions from common files" and "Workflow files are able to import and reuse steps from top-level folders locally". Two platform objects propagate in place as well, API Resources ("reusable connections to your internal API endpoints that can be used to define Requests and Triggers for Workflows") and Environment Secrets, where "the Environment Secret will update in any workflows it's used in". Fix-once is real for a credential and for an internal endpoint. The condition attached to it is that no non-developer touches the workflow: "When making updates in a dashboard to a workflow that is using advanced patterns in Paragraph, the advanced pattern will be a replaced with an inline representation of the resulting steps", and "Git Sync currently cannot recover the use of these abstractions in code." Paragon's remedy is to surrender one of the two surfaces, a one-way Git to Paragon sync that "Works best when only engineering team members will be working on integrations development". Inside the dashboard the documented mechanism for sharing is duplication, "Copy from Project". Reuse across workflows at run time is plumbing: sign a Paragon User Token in a Function step, then trigger the target workflow from a Request step, both counted as billable tasks. Which leaves Marcus's actual question, which trust runs which version of the shift lookup, answered by reading the repository. Paragon does not document a reverse index from a shared piece to the workflows calling it. We searched /apis/api-reference, /apis/task-history, /monitoring/event-logs, /deploying-integrations/projects, the /paragraph pages and the full product-updates changelog. On that basis relating a shared step to its callers is reading the Git repository, if the lookup lives there, rather than asking the platform.
