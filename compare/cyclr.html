02Any data format, any file size

Quarter-end's 80MB file clears by 4am on the same path as a normal night. On Cyclr, the three published push routes cap at 10 MB, so an 80 MB file is collected as a binary file rather than posted.

One unified data processing engine: format-agnostic, large payloads on the ordinary path, one open query standard

Every record, file, and API response flows through a single engine with a small memory footprint. The platform does not care what shape your data arrives in or how much of it there is.

The scenario

Caldera Health's 38 clinics need overnight claims reconciled before 7am doors open.

Caldera Health, a 38-clinic group. Every night at 1am, their practice-management system exports the day's claims and inventory as one file. On a normal Tuesday it is 12MB. At end of quarter it is 80MB. The integration has to parse it, reconcile it against the billing platform, and post corrections before clinics open at 7am. Nobody is awake to babysit it, which is the point.

On APIANT
  1. The AI wrote the reconciliation logic once. The engine normalizes any format into one internal model, so the same transformation runs whether the source sends structured records, spreadsheets, or something custom, and queries use one open standard everywhere.
  2. No per-format branch for the AI to author or a person to maintain. Its memory footprint stays small, so the 80MB quarter-end file takes Tuesday's path: no storage hop, no chunking. Corrections post by 4am.
  3. If a record fails, the AI reads the payload at that step and says what arrived, and Caldera's operator can open the same run herself.

Corrections post by 4am. Quarter end is not an incident category.

On Cyclr

Caldera's quarter-end file reaches Cyclr as a fetch rather than a push, and their own table settles that rather than the clinic group's architect. It publishes "Inbound Webhook payload" at 10 MB, "Synchronous Webhook Response payload" at 10 MB and "Cyclr API call payload" at 10 MB, then 100 MB for an "Encoded and encrypted payload on a single Step within a Transaction" and 100 MB for "Binary files", adding that "Performance can be affected when payloads approach these limits." The 100 MB figure is live and enforced by their own account: release note R26-2 records "Transaction Step maximum data size restored to 100 MB". So 80 MB sits inside the binary-file ceiling their table allows, and eight times above each of the three push routes, which is why the file has to be collected as a file rather than posted to a webhook or pushed through their API.

Format coverage is real, and it is per route. Custom Connector Methods document JSON and XML, with a definable XML root element, and handle zip and gzip responses; delimited text arrives through a utility connector whose method creates "delimited text content, for example Comma Separated Values (CSV) and Tab Separated Values text". The quick route is narrower, and their docs say so plainly: "Note: HTTP Request Steps only support JSON Request and Response data", with the redirect spelled out for anything else, "For a Webhook Step that supports other data types, such as XML, or that uses Field Discovery, see the Generic Webhook Connector, or look into building Custom Connectors." Which formats a Caldera integration can take therefore depends on which connectivity route it was built on, decided months before the file grew.

The reconciliation logic meets its own clocks. Where that logic is script, the published ceilings are 60 seconds for standard event handlers and 90 seconds for `after_action`, which runs per data page, and their guidance notes that "Using 'Inline Script' on a Field Mapping is a lot slower than using Script in a Step's Advanced Settings area." A 12 MB Tuesday and an 80 MB quarter end run against the same numbers.

04 · A deterministic compiler that refuses structurally invalid work before it exists

The scenario

Halvorsen Mutual: 6,200 hail claims ride on a generated payments integration

Halvorsen Mutual writes crop insurance for 8,900 farms across Nebraska and Kansas. After a hail week in June, 6,200 claims queue up, average payout $18,400, and the integration that pushes approved amounts into the payments system was generated last month. It compiled cleanly and it deployed cleanly. Dee Ostergaard, the claims supervisor, is the person who learns whether it wrote the approved amount or the estimate into the payment field, and she learns it from farmers on the phone.

The AI's intent passes through a constrained schema; the compiler refuses invalid structures at the door. It then tests the build on a real saved claim and reads what reached the payment field. Dee can open that run too.

Both fields are numbers. The approved amount and the estimate are both numeric, both required and both mapped, and the checks their build documentation names cannot separate them, because those checks are presence and type. "Steps may be grayed out to indicate that there are required fields to fill out in order for the step to work", "Fields marked with a tick are required and must be mapped", and a type mismatch surfaces as a warning behind a Marketplace setting, "Data Type Mismatch Warnings Enabled", which shows a "data type warning during mapping". Dee's 6,200 claims are not distinguishable by any of those. They do add refusals, and one shipped this year, so credit it: "Split Transaction Validation: System prevents invalid Split Transactions from executing with incorrect parent data references." That is a real gate rather than a warning. It is also scoped to one transaction type, and it acts at execution rather than at build. For a generated integration the question is what a machine can verify before deploy, and that is bounded by what their reference exposes. Across the 101 paths and 142 operations in their published API, the test-shaped operations are three variants of "Tests a connector method" plus two reads, "Gets cycle setup prerequisites" and "Gets step setup prerequisites". A caller can prove one connector method answers and that a step's prerequisites are filled in. Neither of those tells anyone which number reached the payment field, and that is where the comparison sits: a structural refusal at build plus a test run against a real saved claim, against required fields filled plus a data-type warning you switch on. We looked across Create a Template, Template Settings, Test a Template, The Builder and Field Mappings, and completeness is what those pages document.
