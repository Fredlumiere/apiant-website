05 · Reusable building blocks: assemblies, modules, subassemblies

The scenario

Cardwell Staffing: 60 trusts, 60 drifting copies of one shift lookup

Cardwell Staffing places 2,300 agency nurses a week across 60 NHS trusts, each running its own rostering system. The logic that finds available shifts by ward was built once, then copied into all 60 integrations, and a timezone correction made in February reached 41 of the copies. On a Tuesday morning audit call, a trust liaison asks Marcus Ibe, the RevOps lead, to state which version of that lookup each trust is running today.

Marcus asks the AI which integrations run the shift lookup; it names the referencing assemblies and the automations using them. Built once, fixed once: all 60 trusts inherit it. He can walk the list himself.

Concede the reuse unit outright, because n8n has one and it is good. "Use the Execute Sub-workflow node to run a different workflow on the host machine that runs n8n", extracting one is a menu action, "you can also extract selected nodes directly using Sub-workflow conversion in the context menu", release 2.32 made that conversion carry attached AI sub-nodes with it, and the callee declares its own input contract and its own allow-list of who may call it. It is on every tier, including the free Community edition. Built once and fixed once holds on n8n at the workflow layer. What costs something is the question Marcus is asked on the call: which trusts are running which version of the shift lookup today. n8n shipped a dependency index for exactly this in release 2.14, and their release note is explicit that it is more than a screen, so concede it in their own words: "n8n now exposes dependency information for workflows, credentials, and data tables via new API endpoints. Workflow cards can show counts of related credentials, data tables, and sub-workflows, while a details view can list resolved dependency names." Release 2.15 added that "the reverse relationship (which workflows use a given workflow as their error handler) is also shown." What the published surfaces enumerate is narrower than the release note. Their public workflow endpoint reference names its operations one by one, retrieve all, create, update, delete, retrieve a specific version, publish, deactivate, unpublish, archive, unarchive, transfer to another project, retrieve one, retrieve version history, get tags and update tags, and none of them is a dependencies route. Their instance MCP server's tools reference groups its tools into six categories, Workflow management, Execution management, Credential management, Workflow builder, Agent management and Data tables, and the word dependency appears in none of them, while search_workflows filters by name, description, project and tags. @n8n/cli has no dependency command. So the query runs on the instance and is absent from the reference an integrator, or an agent, builds against. The index also stops one layer above the layer n8n's own documentation tells you to watch. The release note names workflows, credentials and data tables, and 2.15 adds error workflows. Node types are not among them, and their community-node page reads: "Node developers may introduce breaking changes in new versions of their nodes ... Depending on the node versioning approach that a node developer chooses, upgrading to a version with a breaking change could cause all workflows using the node to break. Be careful when upgrading your nodes." For sixty trusts on sixty rostering systems, most of which have no built-in node, the shift lookup lives in a node package or an HTTP step, and that is the dimension the index does not name.

The scenario

Alder Pharmacy: 310 branches, one shared rate limit, 2:40am pages

Alder Pharmacy Group dispenses across 310 branches in the north of England, every one of them syncing to a single supplier API that allows 120 calls per 10 seconds. Fourteen other automations draw on that same budget, and the arithmetic that keeps them inside it lives in one engineer's head. Tell the AI the vendor's published limit and it sets the throttle, at connector, action, or connection level, or Sunil types it once himself. Either way the platform enforces it across every automation and every account touching that API, with queueing and backoff, and either of them can read the current setting back. One deployment runs 232 locations against a single 185-calls-per-10-seconds budget.

Pacing against a vendor's ceiling is set inside each workflow that touches that vendor, and the arithmetic is redone whenever another workflow, or another instance, starts drawing on the same credential. The controls n8n publishes are scoped to a node, a loop or an instance. On the HTTP Request node they are "Items per Batch: Enter the number of input items to include in each batch" and "Batch Interval: Enter the time to wait between each batch of requests in milliseconds". Loop Over Items is positioned for exactly this job: "You can batch the data in groups and process these batches. This approach is useful for avoiding API rate limits when processing large incoming data." The per-node retry dials are published as narrow ranges, maxTries "Must be 2-5" and waitBetweenTries "Must be 0-5000". The instance dial counts runs rather than calls, and it excludes the runs a fan-out produces: "Concurrency control applies only to production executions ... It doesn't apply to any other kinds, such as manual executions, sub-workflow executions, or error executions." The missing piece is a shared call budget held against one vendor credential and enforced across many workflows and many accounts. n8n does not document this. We searched control-concurrency, understand-concurrency, the HTTP Request and Loop Over Items node pages, and the executions and queue-mode environment-variable references. On that basis it is manual work rather than a platform behaviour. Their own multi-tenant guidance also puts those settings inside each copy: "Best practice is to have a 'base' workflow that you then duplicate and customize for each new user with their credentials."
